# Hospital Domain Bundle

This is the current healthcare-specific FLOW bundle inside the generic `packages/flow-generator` workspace.

Key files:

Appointment journey source mapping: table "healthcare"."flow_records"; record filter collection = 'appointments'; JSON column "dataJson"; booking source key "dataJson"->>'booking_source'. The generator writes booking_source from {{system.channel}}, so the stored value identifies whether the booking journey entered through the web or WhatsApp channel. Notification delivery channel fields remain separate.

- `APPOINTMENT_SYNC_STANDARD.md`
- `templates-source/hospital-full-automation.source.flow.json`
- `templates/hospital-full-automation.flow.json`
- `templates/assai-deepa-hospital-appointment-single-branch.flow.json`
- `templates-stable/hospital-full-automation.flow.json`
- `WORKFLOW_QA_MATRIX.md`

The import-ready appointment workflow display name is `Sai Deepa Hospital`; its patient-facing bot name is `Sai Deepa Hospital Assistant`.

`APPOINTMENT_SYNC_STANDARD.md` is the canonical shared instruction for all
hospital appointment FLOW generators. It defines the CRM-owned
`healthcare.flow_records` collections, required query filters, live schedule
calculation, reservation and atomic-commit guarantees, failure behavior, and
release tests. The Sai Deepa single-branch export is the current validated
implementation; the legacy full-automation export must not be treated as
compliant until its missing source FLOW is restored or migrated.

Commands from the package root:

```powershell
npm run domain:hospital:build
npm run domain:hospital:validate
npm run domain:hospital:appointment-single-branch:build
npm run domain:hospital:appointment-single-branch:validate
npm run domain:hospital:audit:journeys
npm run domain:hospital:audit:content
```

The Sai Deepa single-branch appointment variant is generated from the stable hospital source flow instead of keeping a second large hand-maintained hospital JSON. Its patient journey is:

`Welcome to Sai Deepa Hospital, Chanda Nagar.` → `📅 Book Appointment` → Mobile Number form → shared WhatsApp and email OTP verification → upcoming appointment details → icon-labeled department input buttons → doctor carousel cards → convenient appointment date and slot → full-detail review → explicit confirmation → reservation hold and `pay_at_hospital` booking → WhatsApp appointment confirmation → exact 12-hour and 2-hour WhatsApp reminders. The opening menu does not show an emergency action or an extra “How can I help you today?” prompt; urgent concerns entered in the department journey still use the emergency-care safety path.

Emergency never requests patient data or OTP. It shows the urgent-care message with the Sai Deepa emergency support number and ends the conversation immediately; no action buttons are shown. `emergency_phone` remains seeded from the verified hospital support phone and must be replaced or explicitly verified before production deployment.

Booking configuration and contracts:

Availability calculations index appointment timestamps once and group reservation
windows by doctor/date. Primary, alternate, and conflict calculations retain the
same slot IDs, capacities, statuses, and leave rules with a bounded 1,000 ms
budget. Each calculation clears its previous inventory before starting. A script
failure takes an explicit `failure` edge to a localized recovery message and ends
the turn; only a successful calculation with empty inventory says no dates were
found. Detailed errors remain in `lastScriptError` and the execution trace after
deploying the matching API runtime change. Deploy that change and re-import the
regenerated single-branch FLOW together; start a new conversation for validation.

- `patient_mobile` accepts `^(?:\+91[\s-]?)?[6-9]\d{9}$` and is normalized to `+91XXXXXXXXXX`; the lookup uses the healthcare patient record’s `mobile_normalized` value. The widget keeps this validation active but hides the technical regex guidance, so patients see a clean Mobile Number field.
- The native OTP node sends the generated OTP through WhatsApp using the approved named-parameter template `verify_otp_usecase`, with `code=OTP` and `text=appointment`; the purpose value stays within Meta's 15-character parameter limit. The template's dynamic URL button at index `0` receives the generated `{{otp}}` value, which is resolved to the six-digit OTP at send time; Meta's approved template owns the base URL, so the full `https://saideepahospitals.com/` URL must not be sent as the button parameter. It has a five-minute expiry, 30-second resend cooldown, three resends, and three attempts. OTP values are never copied into ordinary flow variables. Appointment confirmation and reminders remain WhatsApp-only.
- When OTP verification is exhausted after three attempts, the patient-facing message shows the complete Sai Deepa Hospital contact number `+91 7093762716` and ends the OTP path.
- Existing appointments are queried by `patient_id` only after OTP verification. Only future rows whose scheduled start is strictly later than the current time in `Asia/Kolkata` and whose status is `booked` or `confirmed` are shown.
- Departments are read from `healthcare.departments` for `chanda_nagar` and prepared once as `department_options_text`, `department_map`, and `department_keys`. The export renders the verified Sai Deepa catalog as icon-labeled input buttons because FLOW input buttons do not support dynamic button arrays, with the prompt `Choose the department. If you are not sure, select Not sure / describe issue and type your concern in your own words.` and an explicit `🤔 Not sure / describe issue` action that opens the concern prompt. The concern prompt asks for the patient’s own words and gives three short examples before routing the concern to the matcher. Chat input remains enabled for typed department names or concerns. Direct supported department names continue to booking; a non-matching typed response is sent directly to the concern matcher without asking the patient to repeat it. Numeric replies outside the displayed range are rejected and return through a bounded recovery retry instead of being coerced to a department. A genuine but unclear health concern continues with General Medicine, while clearly junk, unrelated, or non-health input uses a hospital contact fallback and ends the conversation; an urgent or life-threatening concern uses the standard emergency-care message and does not continue routine booking. Regenerate the export after catalog changes so the visible button list stays current.
- Doctors are read from active, booking-enabled `healthcare.doctors` records and shown in a carousel with name, designation, experience, languages, consultation fee, and the DB photo URL (`image_url`, `profile_photo_url`, `profile_image_url`, or `photo_url`) when configured. Availability reads rules, `healthcare.flow_records` collection `doctor_schedule_exceptions`, booking policy, reservations, and appointments. Exception lookup is scoped by `branch_id` and `doctor_scope_key`; active `unavailable`, `leave`, `block`, `closed`, `holiday`, `personal_leave`, `sick_leave`, and `vacation` rows remove the full day when `all_day` is true or only the overlapping `start_time`–`end_time` window otherwise. The appointment node uses only dynamic slots from `appointment_future_slots.data`, `Asia/Kolkata`, and a 30-day horizon; CRM inventory determines the dates and weekly schedule, while the node's permissive `0-6` weekday value is only a renderer compatibility fallback. Synthetic working-hour slots are disabled, so missing CRM inventory cannot create made-up availability. Its configured 32-slot daily presentation limit is large enough to show separate morning and evening sessions.
- Each doctor card also provides `↩️ Change Department`. That action enters a bounded retry policy with three attempts, clears the selected department, doctor, slot, schedule, and reservation variables, and returns to the department chooser. The retry has an explicit exhausted exit; it is not an unrestricted graph loop and never repeats a booking commit.
- Appointment date limits remain enforced internally by the 30-day availability policy, but the date picker does not show technical minimum/maximum value hints to patients.
- New-patient details collect only patient name, age, and gender. Email is not displayed in that form; the optional email field remains in the persisted patient contract for compatibility with existing records and is not required for booking. Gender is shown as `Male` and `Female` while the stored values remain `male` and `female`.
- Selecting `Change Slot` from the review step preserves the selected doctor, department, patient, and session context, then immediately reopens live appointment date and time selection. It uses the same dynamic CRM-backed inventory and slot conflict checks, updates the selected date/time variables from the reselected slot, and shows the full doctor/date/time review before confirmation; it does not restart department or doctor selection and does not repeat any booking commit before the patient confirms again.
- After regenerating this export, re-import it into the active bot workflow. The local Sai Deepa workflow is currently version 6; all primary, alternate, and conflict appointment nodes use `maxSlotsPerDay: 32`. If an older imported version still uses `8`, the runtime will truncate a multi-session day even though the healthcare availability query returns the later session.
- Before confirmation, the patient sees the selected doctor, department, consultation fee, date, time, location, consultation type, and payment mode in one review prompt. The final saved result is a patient-safe confirmation carousel containing only the appointment details needed for the visit; notification and reminder delivery statuses remain internal runtime state.
- After the confirmation carousel, the booking completion end node thanks the patient and closes with: `Thank you for choosing Sai Deepa Hospital. We look forward to assisting you. Have a healthy and pleasant day! 😊`
- Appointment references use the hospital format `SDH-YYMMDD-HHMMSS`, generated at booking time from `Asia/Kolkata` (for example, `SDH-260924-132410`). The same business reference is used by the appointment, reservation, payment, confirmation, reminder, and outbox payloads. A second-level collision must still be rejected by the booking uniqueness/idempotency guard rather than silently overwriting an appointment.
- The confirmation carousel includes a `View location` URL action backed by the readonly global `hospital_location_url` (`https://maps.app.goo.gl/CnLgUZGcaas1Pm776`). For WhatsApp, configure the approved `doc_appointment_confirmed` Meta template with a static URL button labeled `View location` pointing to the same URL; static template buttons do not add a body variable or runtime button parameter.
- Slot capacity is checked against active reservations and `pending_payment`, `booked`, `confirmed`, `checked_in`, and `called` appointments. Fully occupied candidates are retained as `status: "booked"` inventory records so the Appointment node can display them with its configured `hide`, `strikethrough`, or `disable` policy; the selected slot is rechecked at commit time. No reservation or appointment is written until `Confirm appointment` is selected.
- Confirmation button replies are canonicalized to the configured button values before edge routing, so channels that return the visible labels (`Confirm` or `Change Slot`) and channels that return `confirm` or `change_slot` follow the same booking paths. The hold-preparation script calculates the fee in paise before returning, so the payment and appointment record payloads are complete.
- The first-time patient branch assigns `patient_id = PAT-{{patient_mobile}}` before saving the patient record. This is required for the later appointment schema and prevents an empty patient catalog from being misreported as a slot conflict after confirmation.
- Confirmed appointment rows also persist the required `patient_name` and `patient_mobile` values. This keeps Appointment Workflow records self-describing and lets downstream operations surfaces display the booked patient's contact details even while a patient-profile projection is being repaired.
- The commit writes `healthcare.appointment_reservations` and `healthcare.appointments` only after the current review is explicitly confirmed; the `healthcare.payments` pay-at-hospital row is written after both booking records commit. A dedicated confirmation marker gates the commit chain, so change-slot, cancel, timeout, abandoned, or stale paths cannot create an appointment or payment row. Payment IDs use the appointment ID for retry-safe idempotency. A payment-record failure does not roll back an already confirmed appointment or show a false slot-conflict message; it remains an internal operational failure for reconciliation.
- Appointment confirmation uses the approved WhatsApp template `doc_appointment_confirmed` with the exact Meta locale configured by deployment (`en_US`) and maps `1=patient name`, `2=combined appointment date/time`, `3=doctor name`, and `4=a short WhatsApp confirmation code derived from the full appointment ID`. The full UUID-based appointment ID remains in the booking record and web confirmation card; only the WhatsApp value is shortened to stay within Meta's 30-character text-parameter limit. The combined date/time value omits the extra `at` separator so it remains within the same limit. The confirmation node uses one atomic `booking_commit` operation: duplicate protection, reservation confirmation, appointment upsert, pay-at-hospital payment upsert, the domain mutation audit, and a `healthcare.outbox_events` row commit together. The patient-safe confirmation carousel is returned immediately after that durable commit; WhatsApp delivery, reminder scheduling, and secondary audit delivery run from the outbox worker and do not block the booking response. Reminder jobs remain durable Scheduler nodes created by the background post-booking route: both use `{{appointment_scheduled_at}}` (the normalized appointment start, equivalent to `appointmentBooking.start`), `Asia/Kolkata`, `maxExecutions: 1`, `expiryAt: {{appointment_scheduled_at}}`, and `pastTimePolicy: skip`. The 12-hour job uses offset `12 hours before`, trigger text `appointment_reminder_12h`, and the approved template `doc_appointment_reminder`; its variables are `1=appointment date` and `2=appointment time`. The 2-hour job uses offset `2 hours before`, trigger text `appointment_reminder_2h`, and the same approved template. Each trigger routes through a WhatsApp template-message node to `{{patient_mobile}}`. A threshold that has already passed is skipped rather than moved into a business-hours window. Keep `RUNTIME_SCHEDULER_WORKER_ENABLED=true` and the records database connected to the provisioned `healthcare.outbox_events` table; validate delivery with a real approved WhatsApp template and a real opted-in patient mobile.

Reminder deployment prerequisites: configure the approved WhatsApp templates `verify_otp_usecase`, `doc_appointment_confirmed`, and `doc_appointment_reminder` with locale `en_US`, enable the WhatsApp channel, confirm patient opt-in, provision `healthcare.outbox_events`, and run the API with `RUNTIME_SCHEDULER_WORKER_ENABLED=true`. The worker claims the transactional post-booking outbox event, re-enters the flow with `appointment_post_booking_tasks`, and routes the trigger before the normal welcome path so a background task never replays booking instructions. Stale processing locks are retryable and delivery failures are dead-lettered after bounded retries. If an appointment is cancelled or rescheduled, the owning cancellation/reschedule integration must cancel or replace the two old appointment-ID reminder jobs. No dummy appointment data is used.

The schema and tenant-alignment prerequisite `scripts/ensure-sai-deepa-healthcare-schema.sql` aligns the `healthcare.flow_records` family to the current Sai Deepa bot `workspaceId` because runtime record nodes use the workspace as `tenantId`. The canonical `core.tenants` row is also workspace-scoped to that same Sai Deepa `workspaceId`. The script creates an empty workspace-scoped `doctor_schedule_exceptions` collection schema when missing, inserts no exception rows, and does not copy records into `public.flow_records`. Run it against the local database before runtime E2E:

```powershell
Get-Content -Raw -LiteralPath scripts/ensure-sai-deepa-healthcare-schema.sql | docker exec -i pgvector-db psql -U postgres -d code_zero_bot -v ON_ERROR_STOP=1
```

For runtime data, the variant stays collection-oriented in FLOW. With `schemaName: "healthcare"`, the runtime reads and writes the tenant-scoped `healthcare.flow_records` family directly; `collection` remains the logical collection name such as `patients`, `doctors`, or `appointments`. No mirror into `public.flow_records` is required. The healthcare tables must be provisioned before runtime E2E, and the hospital-compatible `branch_*` fields plus generic `location_*` and `scheduled_*_at` fields remain available for downstream healthcare-domain repositories.

This bundle is only one domain implementation. Future industries should follow the same `domains/<industry>/` structure rather than adding their files at the package root.

If hospital flow-specific logic changes, rerun `npm run domains:check` from the package root so the registered bundle rebuilds and validates alongside any other active industries. For local healthcare checks, use `DATABASE_URL=postgresql://postgres:postgres@localhost:5431/code_zero_bot`; the Docker container can be reached with `docker exec pgvector-db psql -U postgres -d code_zero_bot` when `psql` is not installed on Windows.
