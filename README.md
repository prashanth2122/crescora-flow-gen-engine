# External Flow Contract Bundle

Use this bundle when you want an external LLM to generate FLOW import-ready JSON without direct access to the `bot-code-zero` repository.

This standalone package mirrors the application contract from the sibling `bot-code-zero` checkout. Run `npm run contract:generate` after shared node or schema changes; set `BOT_CODE_ZERO_ROOT` when the application checkout is in another location.

Current generator rules include the native `otp` node for backend-only OTP generation and delivery over SMS, WhatsApp, email, or multiple channels. Generated flows must not create OTP values with script nodes, store OTP codes in ordinary variables, or include OTP values in user-visible copy. OTP node configs should keep `resendCooldownSeconds >= 30` and `maxResends <= 3`.

Generated workflows must also read stable customer-visible content from the
bot's Localized Content catalog. Messages, prompts, buttons, forms, carousels,
confirmations, and customer-visible fallback/error copy use stable `{{key}}`
references backed by `bot.localizedVariables`; they are not embedded as
language-specific literals in the graph. New multilingual exports use
`catalog_only`, include `languageSupport`, and provide complete values for every
enabled language. See `WORKSPACE.md` and
`generic-flow-agent-kit/FLOW_GENERATOR_INSTRUCTIONS.md` for the complete
authoring boundary.

Record nodes now support `schemaName` for industry targeting. Generated domain builders default record nodes to the matching schema: `automobile`, `education`, `financial_services`, `healthcare`, `hospitality`, `insurance`, `professional_services`, `realestate`, or `retail`. Use `public` only for legacy/generic flows that intentionally target the default records store.

For any future create or extend work, follow `FLOW_EXTERNAL_LLM_CONTRACT.md` and verify against the relevant domain QA checklist before import. The contract now calls out the recurring mistakes we want to avoid: invented fields, unresolved variables, backward loops, dummy content, and default human handover for routine work. It also expects real database-backed data for persisted flow state. The checklist is workflow-wide; hospital is only one example domain bundle.

The package now treats domain bundles as registered assets. `domains/registry.json` is the list of bundles that must be rebuilt and revalidated whenever flow-specific generation, validation, or contract behavior changes.

## Give the LLM these files

1. `FLOW_EXTERNAL_LLM_CONTRACT.md`

4. Optionally `flow-valid-export.example.json`

## Domain layout

- `domains/<industry>/templates-source/` holds canonical editable source flows for a domain.
- `domains/<industry>/templates/` holds import-ready generated exports for that domain.
- `domains/<industry>/templates-stable/` can hold stable snapshots or rollback-safe reference exports for that domain.
- `domains/<industry>/WORKFLOW_QA_MATRIX.md` holds the domain-specific QA checklist.
- `domains/registry.json` is the authoritative list of domain bundles that package-level sync/check commands update.

## Sync rule

Whenever flow-specific generation logic, validator logic, node/schema contract behavior, or a domain source flow changes, rerun the registered domain sync:

```powershell
npm run domains:check
npm run test:localized-content
```

That command rebuilds and validates every domain listed in `domains/registry.json` so this package stays in sync with application code and domain artifacts together.

For local healthcare runtime E2E, use `DATABASE_URL=postgresql://postgres:postgres@localhost:5431/code_zero_bot`. Run `scripts/ensure-sai-deepa-healthcare-schema.sql` against that database before testing the Sai Deepa appointment bot. The script aligns healthcare record `tenantId` values to the bot `workspaceId`, which is the runtime record-node tenant. The runtime uses the tenant-scoped `healthcare.flow_records` family directly when record nodes select `schemaName: "healthcare"`; no mirror into `public.flow_records` is required. The legacy-named `scripts/sync-sai-deepa-runtime-records.sql` is read-only and only validates the direct healthcare data path.

The full hospital appointment booking path starts with the patient's mobile number, immediately asks for a 6-digit OTP, checks the `patients` collection, hydrates existing patient variables from the saved profile when present, and shows any active confirmed future appointment before asking whether to proceed with another booking. Doctor availability, doctor profile, department guidance, and locations booking all enter this same mobile-first booking spine. The doctor availability and doctor profile journeys now begin with hospital branch selection, then department selection, and only then list the matching doctors for that branch scope. Department lists are no longer hardcoded in the flow JSON: each fresh journey now refreshes the `departments` collection once through a shared catalog step, and booking, department guidance, doctor availability, doctor profile, and online consultation all reuse those prepared variables instead of running their own department lookups. In the doctor profile journey, once a patient selects a doctor, the flow moves straight into phone lookup and OTP verification, shows future confirmed appointments for that patient when present, and only then continues into the shared doctor-specific booking steps for consultation mode, branch, slot, payment, and confirmation. In the booking department picker, selecting `Not sure / describe issue` or typing a free-text concern now routes through a dedicated concern-resolution AI step before doctor fetch, while direct department picks continue straight to booking. When the booking doctor fetch returns exactly one valid doctor, the flow now shows that doctor summary first and then renders a `Proceed` button instead of asking the patient to type `1`. The same single-result rule now applies to other selection journeys that return one valid record, such as a single follow-up source appointment or a single available branch for the chosen doctor. New-patient forms no longer ask for nearest branch or area, and the captured mobile number is reused for the patient record without reintroducing that field into downstream writes. Lookup failures stop safely instead of creating duplicate patient or appointment records. The current full-source OTP gate accepts any 6-digit OTP, allows up to 3 invalid format attempts per journey before ending with a restart message, and records the OTP mode in `metadata.mobileOtpVerificationMode = "accept_any_6_digit_code"` so future implementations can replace it with a real OTP service without changing the journey shape.

The appointment-only single-branch variant at `domains/hospital/templates/assai-deepa-hospital-appointment-single-branch.flow.json` is narrower and stricter. It opens with the two requested actions, verifies the patient through the native email OTP node before patient lookup, and ends with hospital call guidance if delivery fails or verification attempts are exhausted. Emergency exits without patient data capture. Booking then loads a reusable DB-backed department catalog, filters booking-enabled doctors, calculates live availability from recurring rules, exceptions, policy, reservations, and appointments, requires an explicit confirmation before holding a slot, confirms with `pay_at_hospital` only, sends the appointment confirmation to the temporary `prashanth.chinala@gmail.com` email destination, creates two one-shot appointment-start-based Scheduler jobs at 12 hours and 2 hours before the visit, and routes their trigger text to separate transactional WhatsApp template-message nodes. To stay compatible with the healthcare-domain runtime direction, the variant still uses logical collections like `appointments` and `appointment_reservations`, but the appointment and reservation payloads also include generic `location_id`, `location_name`, `scheduled_start_at`, and `scheduled_end_at` fields alongside the current hospital `branch_*` fields.

Availability is now derived from recurring schedule data, not pre-seeded slot rows. The flow reads `doctor_availability_rules`, `doctor_schedule_exceptions`, `appointment_booking_policies`, and active `appointment_reservations`, then calculates slots for the next 31 days in-flow before rendering the appointment node. The slot normalizer produces a strict `{ id, slot_id, reservation_key, date, start, end, label }` shape, removes past times, applies booking-policy cutoffs, respects blocked exceptions, and marks held or confirmed reservations that occupy the same time window as `status: "booked"` rather than dropping them. The Appointment node then applies its configured booked-slot display policy. User-facing slot labels are time-only to avoid repeated date formats in the widget.

When a patient picks a slot, the flow writes a reservation hold into `appointment_reservations`, supports both `pay_now` and `pay_at_hospital`, captures `payment_status` for both branches, confirms the reservation after payment choice, and releases the held reservation if the payment path is abandoned or fails. The payment choice step now keeps the payment question inside the summary message and shows only the action buttons in the follow-up node, which removes the duplicated payment prompt seen in the widget while keeping the same persisted payment behavior. Appointment records persist the reservation metadata (`reservation_id`, `reservation_key`) alongside doctor, branch, and payment details so reschedule and cancel journeys can safely update the same operational record later. Inventory and reservation state now use operational identifiers such as `reservation_id`, `reservation_key`, `hold_id`, `held_by_session`, and `appointment_id`; patient PII remains in `patients` and `appointments` records.

For the single-branch client variant, the same hold and confirmation flow persists those identifiers plus `location_*` and `scheduled_*_at` fields so healthcare-domain repositories can schedule reminders and scope the appointment without reconstructing a timestamp from separate date/time strings.

The reschedule path is also DB-backed. It starts with registered mobile validation plus the same 6-digit OTP gate with 3 invalid-format retry attempts, lists only `status: "confirmed"` appointments, filters them to future appointment dates and times in-flow, shows one or multiple eligible appointment options, and asks the patient which appointment to reschedule when more than one future appointment exists. It then fetches future `status: "available"` slots for the same doctor, branch, and consultation mode, holds the new slot, creates a new confirmed appointment, cancels the old appointment, releases the old slot back to available, sends confirmation, and writes an audit entry. Past appointments must be moved out of `confirmed` status by the hospital backend or scheduled maintenance job so the flow only exposes real future appointments for reschedule.

The cancel appointment path is a separate self-service journey, not a branch of booking. It starts with the registered mobile number and the same 6-digit OTP gate with 3 invalid-format retry attempts, lists only future date-and-time `status: "confirmed"` appointments, asks the patient to select one when multiple future appointments exist, confirms the cancellation, updates the selected appointment to `cancelled`, releases the booked slot back to `available`, sends a cancellation notification, writes an audit entry, and ends with clear refund guidance. Refund copy should state that the finance team will contact the patient if refund processing is applicable under hospital policy.

The follow-up booking path is now self-service. It starts with the registered mobile number and the same 6-digit OTP gate with 3 invalid-format retry attempts, hydrates the patient profile, lists only past dated appointments that are eligible for follow-up, asks the patient which past appointment needs the follow-up, and then locks the booking context to the same doctor before continuing into the shared appointment slot, payment, confirmation, and reminder path.

The lab test path is now split into two simple service modes. For `hospital_visit`, the bot tells the patient that no appointment is required and that they can directly visit the branch. For `home_collection`, the bot collects the patient name, test name, mobile number, detailed address fields, and a future preferred date and time window, saves the request in `lab_requests`, and confirms that a lab technician will contact the patient to finalize the visit.

The report status path now starts with the registered mobile number, asks for the same 6-digit OTP verification with 3 invalid-format retry attempts used in the other self-service journeys, and then shows downloadable lab report links for the current preview environment. The older `report_id` lookup path is removed from this source flow until real report records and secure document delivery are wired back in.

The pharmacy help path is now branch-first. It asks the patient to choose the branch, maps that selection to the branch used elsewhere in the hospital flow, and then shows a branch-specific pharmacy contact number with clear guidance that the pharmacy team can help with medicine availability, refill questions, and prescription-related concerns. The older support-ticket and callback path is removed from this source flow.

The insurance help path is now mobile-first. It asks for the registered mobile number, requires the same 6-digit OTP verification with 3 invalid-format retry attempts used in the other self-service journeys, collects the insurance document upload, runs OCR field extraction, normalizes insurer and policy details into the `insurance_cases` record, queues the case to the insurance support team, and confirms to the patient that the insurance desk will review the extracted details and contact them through approved hospital channels.

Doctor profile and availability journeys expect maintained `doctors` records with qualification, language, branch, consultation mode, fee, profile summary, image URL, `doctor_scope_key`, and active schedule-backed branch/mode combinations. The current source flow is aligned to the recurring-schedule seed data for branches such as `jubilee_hills_branch`, `miyapur_branch`, `kukatpally_branch`, `madeenaguda_branch`, plus `online` for virtual consultations. Doctor rows alone are not enough for booking; production data must also maintain `doctor_availability_rules`, `doctor_schedule_exceptions`, `appointment_booking_policies`, and `appointment_reservations`. The doctor-availability and doctor-profile discovery journeys now start with branch selection, then department selection, and then show only matching doctors for that branch scope. When a department or doctor lookup produces exactly one valid result, the flow now shows that result first and switches to a direct proceed step instead of asking the patient to type `1` for a one-item list. In the booking journey that step is a single `Proceed` action after the doctor details are shown; in availability and doctor profile journeys it remains an explicit confirmation step before booking continues. The same rule is now applied to single-branch and single-follow-up-selection cases as well. When multiple options are available, the numbered-selection step remains in place. After the doctor list is shown, the availability journey uses explicit `Yes` and `No` buttons for the booking confirmation step instead of relying on implicit decision rendering. Department guidance now starts with free-text symptoms, uses the `ai-grounded` Concern Resolution AI node with explicit department-routing context plus user concern input, tolerates freeform model output during post-processing as long as a valid department can be inferred, shows the matched department to the patient, and then continues into the same doctor-availability booking path with a manual department fallback and an emergency-safe branch. The booking flow uses the same concern-resolution logic for `Not sure / describe issue`, and manual fallback selections now route `Emergency Medicine` to the emergency-safe branch instead of continuing into routine booking. Online consultation now follows the same booking engine instead of a support-ticket path: it starts with patient mobile lookup plus the same 6-digit OTP gate, asks for the department, lists only doctors who support `consultation_mode = online` for that department, continues into slot selection, and sends the user directly to online payment without a `pay_at_hospital` branch. New online patients provide the remaining profile details only after the doctor context is chosen and before slot confirmation. This hospital source flow intentionally removes visible consent prompt nodes across journeys for demo smoothness; regulated deployments should add a compliant consent mechanism outside this patient-facing demo path if required. Queue nodes include priority, SLA, skills, and patient context for operational handoff.

Design rule: generated journeys must be automation-first. Do not use human handover as the default path for routine workflows. Use one main intent router only; do not add nested category intent routers. The main intent router should directly include all concrete journeys, such as book appointment, cancel appointment, doctor profile, lab tests, billing, and insurance. Routine hospital services should collect details, save or update the relevant record, send confirmation or instructions, schedule reminders when needed, audit sensitive access, and end cleanly. Appointment booking should follow: Mobile Lookup -> Existing Patient Hydration or New Patient Prep -> Active Appointment Check -> Remaining Patient Details for New Patient -> Branch Selection -> Consultation Type -> Department Selection with Not Sure option -> Fetch Doctors -> Doctor Selection -> Appointment Slot Selection -> Duplicate Check -> Appointment Summary -> Payment Choice -> Pay Now or Pay at Hospital -> Save Payment Status -> Save and Confirm Appointment -> Send Confirmation -> Schedule Reminder -> Next Options -> End. Appointment reschedule should follow: Mobile Lookup -> Future Appointment List -> Appointment Selection -> Show Appointment Details -> Reschedule Confirmation -> Fetch Future Available Slots -> Slot Selection -> Duplicate Check -> Hold New Slot -> Final Summary -> Book New Slot -> Create New Appointment -> Cancel Old Appointment -> Release Old Slot -> Notify -> Audit -> End. Appointment cancellation should follow: Mobile Lookup -> Future Appointment List -> Appointment Selection when needed -> Show Appointment Details -> Cancellation Confirmation -> Cancel Appointment Record -> Release Booked Slot -> Notify -> Audit -> Refund Guidance -> End. Use queues or handover only for emergencies, ambulance coordination, explicit talk-to-hospital requests, sensitive human decisions, unavailable operational data, or true system/integration failures.

Operational record rule: generated workflows must not depend on `encryptPii: true` unless the target deployment explicitly validates `RECORD_PII_ENCRYPTION_KEY` before the journey starts. A missing encryption key makes record nodes fail at runtime. For import-ready self-service templates, keep `encryptPii: false` in generated record nodes and do not put patient PII into inventory, slot, hold, lock, queue-state, or other operational state collections. If a regulated deployment requires field-level encryption, enable it only with a deployment preflight and update the audit expectations at the same time. For industry bundles, set record `schemaName` to the matching industry schema instead of encoding the schema into `collection`.

SQL generation rule: when producing ad hoc PostgreSQL scripts for persisted FLOW data in this workspace, use `public.flow_records` as the default target table unless the request explicitly names another schema or table.

The validator now compiles every `script` node body as JavaScript before passing the export. This catches malformed multiline strings, broken regex literals, and other `Invalid or unexpected token` failures locally instead of during `/bots/import` or runtime execution.

Generated FLOW graphs reject ordinary cycles. To let a patient change an earlier department choice without duplicating the journey, use a `retry` node with `maxRetries` from 1 to 4, one `isRetry: true` edge back to the original input/form/decision, and one `isDefault: true` exhausted exit edge. Set `resetVariables` to the dependent choices that must be cleared (such as doctor and slot); perform booking writes only after final confirmation. The local validator and `/bots/import` still reject unbounded backward edges as `INFINITE_LOOP`.

For example, route `department_input` to `department_confirmation`. Its No branch enters `department_retry`; that node's return edge targets the original `department_input`, while its default edge offers cancellation or a menu after the attempt limit. The Yes branch proceeds to the shared slot and booking steps. Keep department/doctor/slot state current as answers change, and store a booking only on the confirmed branch.

The validator intentionally treats appointment `dateVar` values as non-import-safe for generated templates. Resolve the selected slot from the appointment node `outputVar`, then use that normalized slot object for downstream record data unless the deployed FLOW import validator is confirmed to accept `dateVar` reads.
